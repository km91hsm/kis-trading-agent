# SaveTicker 리플랫폼 사전 검증

## 범위와 현재 상태

사용자 요청: 브라우저 창의 반복 표시를 줄이고 수집을 안정화한다. 재로그인, 세션·쿠키 초기화와 다른 수집 방법을 실제로 비교한다. 뉴스 본문·리포트 PDF, 커뮤니티 지수/상승/하락/TOP5, 증시 거래대금/상승/하락, 캘린더를 유지한다. 모의·실거래 운영 변경은 제외한다.

원격 main `89584fa`에서 별도 worktree `feat/saveticker-replatform`을 만들었다. 실행 중인 매매 프로그램은 변경하지 않는다. 현재 확장/Native host는 이전 `trading-agent/dist/trader`의 수집 폴더를 사용하며 이번 조사에서는 이 의존성을 보존한다.

## 진단 패치 요구사항

- API 실패를 일괄 `api_request_failed`로 덮지 않고, 허용 목록의 원인 코드와 실패 단계(begin/fetch/prepare/detail/snapshot/pdf)를 보존한다.
- PDF 실패는 응답 수신, 다운로드, 저장 단계를 구분한다.
- 예외 원문, URL, 계정, 쿠키, 비밀번호, 응답 본문을 진단 상태에 기록하지 않는다. 알 수 없는 오류는 고정된 일반 코드로 바꾼다.
- 팝업은 단계와 원인 코드를 보여준다. PDF 실패가 있는데 “현재 기록된 수집 오류가 없습니다”라고 표시하지 않는다.
- 수집 요청의 허용 범위, 재시도 예산, 로그인 동작 및 거래 기능은 이 패치에서 변경하지 않는다.

## 다음 비교 및 설계 후보

- 세이브티커 도메인만 대상으로 쿠키·사이트 데이터 초기화 후 재로그인. 다른 사이트의 로그인은 유지한다.
- 쿠키가 없는 별도 세션/프로필과 기존 세션 재사용 비교.
- 현재 수집기의 headless 모드를 격리된 저장 폴더에서 한 번 실행해 최신 환경에서 재검증.
- 요청을 직렬화하고 수집 주기를 낮춘 경우, 정상 HTML 페이지 갱신을 하는 경우를 구분하여 관찰.
- 공식 API·내보내기 제공 여부 확인. 공개 API 문서를 아직 확인하지 못했으며 현재 내부 엔드포인트를 공식 제공 API라고 부르지 않는다.

권장 구조 초안: 거래 데몬과 분리된 수집 서비스 → 단일 세션 관리자 → 브라우저/지원 API 어댑터 → 기존 정규화·저장 계약. 복구는 대기 → 페이지 갱신 → 전용 탭 재생성 → 재로그인 → 사이트 데이터 초기화 → 새 프로필 순서로, 원인별·횟수 제한을 둔다. 재로그인과 쿠키 삭제를 무한 반복하지 않는다. 기존 유효 데이터를 보존하고 스트림별 성공 시각/실패/누락/PDF 상태를 Web UI에 표시한다.

## 코드 검증

실패 테스트를 먼저 추가해 기존 코드의 원인 유실과 PDF 오류 표시 누락을 재현했다. 독립 리뷰에서 다운로드 중단의 저장 단계 오분류와 Native PDF 오류 유실을 발견해 추가 실패 테스트 후 수정했다. DOM 모드 오류에 과거 API 단계가 붙지 않게 했다. 수정 후 확장 전체 테스트 170개 통과(2026-11-06), 두 리뷰의 재검토에서 중요 이슈 없음. 사이트의 장시간 수집 성공과 전체 데이터 완전성을 의미하지 않는다.

17:55 진단 패치의 api-runner.js/worker.js/popup.js 3개를 기존 확장 패키지에 백업 후 적용했고 Chrome에서 확장을 새로고침했다. Native host 및 매매 앱은 변경하지 않았다. 설치본과 worktree 파일 해시 일치를 확인했다. 기존 파일은 같은 패키지의 diagnostics-backup-20261106_175501에 보관한다.

17:54 `pmset -g assertions`에서 ChatGPT의 `NoIdleSleepAssertion`과 시스템 잠자기 방지 활성화를 확인했다. 이는 화면 잠금 해제나 화면 조작 접근을 보장하지 않는다. 17:59 다시 `IOConsoleLocked=True`였으며 이때 Chrome UI는 cgWindowNotFound로 접근 불가였다. 당시 초기화 후 수집기는 중지 상태였고 정상 HTML 갱신 35분 시험은 시작하지 못했다. 19:12 정상 페이지 및 기본 그룹 응답 확인 후 실제 시험을 시작했다. 4분 간격 최대 8회, 35분 뒤 자동 중지하며 진행 중인 시험에는 새 코드를 적용하지 않는다.

Web UI 재시작 요청은 확장 모드에서 EXTENSION_NOTE 안내만 반환한다. 향후 리플랫폼에서 팝업 외부의 제어 경로를 추가할 후보이며, 현재 구현됐다고 표시하면 안 된다. 화면 잠금을 프로그램으로 우회하거나 브라우저 쿠키 DB를 직접 수정하지 않는다.

## PDF 파일명 보완 요구사항과 증거

19:13 실제 PDF 응답은 다운로드되었으나 `Downloads/SaveTicker/<발급 파일명>.pdf` 대신 `Downloads/<임의 이름>.pdf`에 저장되었다. 파일 크기와 PDF 서명은 유효했고, 경로 검증에서 거절된 것으로 판단한다. Chrome 문서는 다른 확장의 파일명 결정 처리기가 요청한 파일명에 영향을 줄 수 있다고 설명한다. 특정 확장이 원인이라는 점은 아직 확인하지 않았다.

- 현재 활성 수집의 정확한 URL, 이 확장의 ID, PDF MIME, 유효 시간, 다운로드 ID를 확인한 경우만 발급 파일명을 제안한다. 아직 ID가 반환되지 않았다면 파일명을 제안할 수 있지만 ID를 선점하지 않는다.
- 다른 다운로드, 취소·만료·중지된 작업은 원래 파일명을 유지한다. Native의 정확한 경로·ticket·파일 검증은 그대로 유지한다.
- 실제 파일명이 다르면 일반 API 실패로 덮지 않고 `filename_unverified`와 다운로드 단계를 표시한다.
- 설치본 버전으로 수정 여부를 식별할 수 있도록 1.4.1로 올린다.

합성 다운로드에서 원래 파일명이 무시되는 상황을 먼저 실패 테스트로 재현했다. 파일명 제안과 ID 소유권 분리, 관계없는 다운로드 무변경, 만료·취소·잘못된 출처 거절, 실패 원인 보존을 검증한다. 독립 규칙/요구사항 리뷰에서 실제 Native ticket 만료 시각과 DOM 오류 단계 표시를 추가 보완했다. 재검토 중요 이슈 없음, 확장 전체 175개 테스트 통과. 실제 사이트 적용 결과는 시험 종료 후 별도로 기록한다.

- https://developer.chrome.com/docs/extensions/reference/api/downloads

## 정상 HTML 갱신 시험 결과와 잠금 범위

19:12부터 실제 저장을 확인했으나 19:26:12.260 마지막 유효 저장 후 19:26:19.576 Native runtime이 `paused / extension_disconnected`가 되었다. 35분 시험은 완료하지 못했다. 설정은 4분 간격 최대 8회였다. 19:40 잠금 해제 후 팝업에서 실제 정상 갱신 3/8회, 서버 보안 확인 응답 감지와 전체 사용자 확인 대기를 확인했다. `extension_disconnected`는 종료 결과이며 사이트 차단 또는 macOS 잠금이 원인임을 입증하지 않는다.

모니터는 19:24:13부터 `IOConsoleLocked=True`를 확인했고 19:26:13까지 `collecting`을 관찰했다. 잠금 상태에서 약 2분간 저장이 이어졌지만 35분 잠금 성공으로 확대하지 않는다. 시험 중 새 코드는 설치본에 적용하지 않았다.

시험 구간에서 대상 20개 스트림의 capture 기록이 생성되었다. 뉴스 최신 20개 중 12개에는 본문이 있었고 나머지는 본문 없는 기사 상태였다. 2027년 1월·2월 캘린더 응답은 0건이며 데이터 확보 성공으로 계산하지 않는다. PDF는 파일 다운로드 이후 저장 검증에 실패했다. 모든 스트림은 제한된 범위의 `partial` 수집이며 전체 과거 데이터 완전성을 보장하지 않는다.

1.4.1은 확장 전체 175개 테스트와 독립 리뷰를 통과했다. 로컬 실제 Chromium 통합 시험은 Chromium 미설치로 1개 skipped이며 실제 PDF 저장 성공의 증거가 아니다. 새 커밋 CI에서 기존 stale 정리 테스트가 실제 스케줄러의 잡과 경합해 실패했다(3573 passed, 24 skipped, 1 failed). 해당 테스트만 scheduler를 paused로 시작하고 종료를 기다려 기동 정리의 검증 범위를 격리한다. 운영 데몬 코드는 바꾸지 않는다.

공식 출처와 운영 대안은 [화면 개입·세션 신뢰성 조사](2026-11-06-saveticker-operation-options.md)에 정리했다. 종료 원인 확인과 PDF 수정본의 실제 저장 검증은 아래 후속 확인으로 완료했으며 자동 복구의 장시간 지속성은 별도 관찰한다.

## 1.4.1 실제 적용과 PDF 저장 확인

19:41 기존 설치 파일이 진단 패치 기준과 일치하는지 확인하고 6개 확장 파일을 백업한 뒤 적용했다. Chrome 확장 상세에서 1.4.1과 새로고침 완료, 재개 후 팝업에서 확장/수집기 모두 1.4.1을 확인했다. Native host와 매매 앱은 변경하지 않았다.

19:43:49 실제 리포트 PDF 1건이 저장되었다. `Downloads/SaveTicker`에 발급된 파일명으로 내려온 6,895,551바이트, 31페이지 PDF가 수집 attachments에 연결되었다. PDF 서명과 SHA-256 파일명 일치, 추출 텍스트 파일 존재를 확인했다. 팝업도 `PDF 저장 완료 (saved)`였다. 원문 내용은 이 기록이나 fixture에 넣지 않는다.

주기적 HTML 시험은 껐고, 사건당 1회 자동 새로고침과 정상 저장 10분 후 다음 사건 복구 허용, 전용 창 최소화 유지를 켠 상태로 19:43 재개했다. 이는 기존의 횟수 제한 복구 기능을 실제 비교하는 과정이며 무기한 안정성을 입증한 것은 아니다.
