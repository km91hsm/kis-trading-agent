# SaveTicker 리플랫폼 사전 검증

## 범위와 현재 상태

사용자 요청: 브라우저 창의 반복 표시를 줄이고 수집을 안정화한다. 재로그인, 세션·쿠키 초기화와 다른 수집 방법을 실제로 비교한다. 뉴스 본문·리포트 PDF, 커뮤니티 지수/상승/하락/TOP5, 증시 거래대금/상승/하락, 캘린더를 유지한다. 모의·실거래 운영 변경은 제외한다.

원격 main `89584fa`에서 별도 worktree `feat/saveticker-replatform`을 만들었다. 실행 중인 매매 프로그램은 변경하지 않는다. 현재 확장/Native host는 이전 `trading-agent/dist/trader`의 수집 폴더를 사용하며 이번 조사에서는 이 의존성을 보존한다.

## 진단 패치 요구사항

- API 실패를 일괄 `api_request_failed`로 덮지 않고, 허용 목록의 원인 코드와 실패 단계(begin/fetch/prepare/detail/snapshot/pdf)를 보존한다.
- PDF 실패는 응답 수신, 다운로드, 저장 단계를 구분한다.
- 예외 원문, URL, 계정, 쿠키, 비밀번호, 응답 본문을 진단 상태에 기록하지 않는다. 알 수 없는 오류는 고정된 일반 코드로 바꾼다.
- 팝업은 단계와 원인 코드를 보여준다. PDF 실패가 있는데 “현재 기록된 수집 오류가 없습니다”라고 표시하지 않는다.
- 수집 요청의 허용 범위, 재시도 예산, 로그인 동작 및 거래 기능은 이 패치에서 변경하지 않는다.

## 다음 비교 및 설계 후보

- 세이브티커 도메인만 대상으로 쿠키·사이트 데이터 초기화 후 재로그인. 다른 사이트의 로그인은 유지한다.
- 쿠키가 없는 별도 세션/프로필과 기존 세션 재사용 비교.
- 현재 수집기의 headless 모드를 격리된 저장 폴더에서 한 번 실행해 최신 환경에서 재검증.
- 요청을 직렬화하고 수집 주기를 낮춘 경우, 정상 HTML 페이지 갱신을 하는 경우를 구분하여 관찰.
- 공식 API·내보내기 제공 여부 확인. 공개 API 문서를 아직 확인하지 못했으며 현재 내부 엔드포인트를 공식 제공 API라고 부르지 않는다.

권장 구조 초안: 거래 데몬과 분리된 수집 서비스 → 단일 세션 관리자 → 브라우저/지원 API 어댑터 → 기존 정규화·저장 계약. 복구는 대기 → 페이지 갱신 → 전용 탭 재생성 → 재로그인 → 사이트 데이터 초기화 → 새 프로필 순서로, 원인별·횟수 제한을 둔다. 재로그인과 쿠키 삭제를 무한 반복하지 않는다. 기존 유효 데이터를 보존하고 스트림별 성공 시각/실패/누락/PDF 상태를 Web UI에 표시한다.

Cloudflare의 JavaScript Detections는 HTML 응답에 삽입되고 유효 기간이 15분이라는 공식 설명이 있다. 이전 약 13분 뒤 재확인은 관련 가설을 세울 근거이나, 세이브티커의 실제 서버 규칙을 확인한 것은 아니다. 정상 페이지 갱신과 요청 주기 조정을 분리 시험해야 한다.

## 코드 검증

실패 테스트를 먼저 추가해 기존 코드의 원인 유실과 PDF 오류 표시 누락을 재현했다. 독립 리뷰에서 다운로드 중단의 저장 단계 오분류와 Native PDF 오류 유실을 발견해 추가 실패 테스트 후 수정했다. DOM 모드 오류에 과거 API 단계가 붙지 않게 했다. 수정 후 확장 전체 테스트 170개 통과(2026-11-06), 두 리뷰의 재검토에서 중요 이슈 없음. 사이트의 장시간 수집 성공과 전체 데이터 완전성을 의미하지 않는다.

진단 패치는 worktree에만 있으며 현재 설치된 확장/Native host에 아직 배포하지 않았다. 쿠키 초기화와 패치 배포 후 PDF 실패 원인 확인이 다음 실행 항목이다. 화면 잠금을 프로그램으로 우회하거나 브라우저의 쿠키 DB를 직접 수정하지 않는다.
